# ADR-0007: выделение ядер под прерывания и плоскости

> [!abstract] Суть
> «Выделить ядро под прерывания» — это не один флаг, а четыре независимые вещи: инициализация GICR этого ядра, свой `VBAR_EL1`, свои MMU/кэши и маршрутизация конкретного INTID на нужное ядро. Выделение ядра убирает конкуренцию за CPU, но не убирает стоимость входа в исключение и промахи кэша. Рекомендация: ядро 0 — data plane run-to-completion, ядро 1 — control plane, остальные припаркованы. «IRQ-ядро», которое перекладывает пакеты рабочим, — антипаттерн.

## Контекст

Нужны метрики на поток: EMA для RTT/джиттера, межпакетные интервалы, TTL-статистика. Возник вопрос: не отдать ли одно-два ядра под обработку прерываний, чтобы убрать неопределённость.

Текущее состояние: активно одно ядро, остальные в `wfi`-парковке ([[entry_hygiene]]); GIC инициализируется только для ядра 0.

## Что технически значит «выделить ядро»

| Шаг | Что сделать | Почему |
|---|---|---|
| 1. Разбудить | PSCI `CPU_ON` (SMC/HVC) или mailbox+`sev` | вторичные ядра стоят в `wfi` |
| 2. Свой стек | per-core `SP`, выровнен на 16 | иначе ядра затрут кадры друг друга |
| 3. Своя MMU | `TTBR0_EL1`, `TCR`, `MAIR`, `SCTLR` на каждом ядре | эти регистры per-core; таблицы можно разделять |
| 4. Свой `VBAR_EL1` | записать адрес таблицы векторов | `VBAR_EL1` — per-core |
| 5. Свой GICR | `GICR_WAKER`, `IGROUPR0`, `IPRIORITYR`, `ISENABLER0` **своего** редистрибьютора | сейчас в `gic.rs` жёстко `gicr_for_core(0)` |
| 6. Маршрут SPI | `GICD_IROUTER<n>` = affinity целевого ядра | для PPI маршрут не нужен: они banked per-core |
| 7. CPU interface | `ICC_SRE_EL1`, `ICC_PMR_EL1`, `ICC_IGRPEN1_EL1` | sysreg-ы per-core; вызов `GIC.init()` на ядре 1 сейчас настраивает **чужой** GICR |

Проверка affinity: `MPIDR_EL1`. В `start.s` сейчас `and x0, x0, #3` — это только Aff0. Для RK3566 (4 ядра, один кластер) и QEMU virt этого хватает, но корректнее сравнивать `Aff0 | Aff1<<8 | Aff2<<16`.

> [!warning] Находка в текущем `start.s`
> Парковка (`cbnz x0, park`) стоит **до** `msr daifset, #0xf`. Если firmware оставило прерывания включёнными, вторичное ядро войдёт в `wfi` с `PSTATE.I=0` и без валидного `VBAR` — при первом же прерывании уйдёт в fault по адресу 0. Маску надо ставить до ветвления на `park`.

## Что даёт выделение ядра по джиттеру

Бюджет «IRQ asserted → метка времени взята»:

| Компонент | Убирается выделением ядра? |
|---|---|
| Вытеснение задачей/executor'ом на том же ядре | **да** |
| Замаскированные IRQ в чужих критических секциях | **да** |
| Арбитраж GIC с другими IRQ того же ядра | да, если INTID'ы разведены |
| Вход в исключение (GIC ack + вектор) | нет |
| Промах I-кэша на векторе и первых инструкциях | нет (лечится «горячим» ISR) |
| Промах D-кэша/TLB на дескрипторе | нет |
| Конкуренция за шину/DRAM с другими ядрами | нет |
| DMA и cache maintenance | нет |

Вывод: выделение ядра убирает **конкуренцию**, а не **физику**. Если метка берётся в ISR до попадания в очередь, последующая загрузка ядра метрику уже не портит — она портит только скорость реакции.

## Одно или два ядра: арифметика

1 Гбит/с, минимальный кадр 64 Б + 20 Б overhead (преамбула + IFG) = 672 бита:

```text
1e9 / 672 ≈ 1.49 Mpps на порт
2 порта (worst case, оба залиты 64-байтными) ≈ 2.98 Mpps
бюджет на пакет на одном ядре ≈ 672 нс ≈ 1000–1200 циклов при 1.6–1.8 ГГц
```

Для 1500-байтных кадров это всего ~81 kpps на порт — один A55 справляется с запасом.

Ключевое ограничение — не CPU, а **число очередей NIC**. Если у MAC одна RX/TX-очередь (типично для RTL8111 и, вероятно, для GMAC RK3566 — проверить по TRM), два ядра будут драться за один дескрипторный ринг: это не параллелизм, а лишние атомики и false sharing.

| Схема | Когда имеет смысл | Цена |
|---|---|---|
| 1 DP + 1 CP | всегда; рекомендуется | нет |
| 2 DP, порт на ядро | 2 очереди RX, каждый порт свой | форвардинг A→B идёт через кросс-ядерную очередь |
| 2 DP, flow sharding (RSS) | NIC умеет несколько очередей + хэш по потоку | нужен RSS и per-queue TX |
| «IRQ-ядро» + рабочие | почти никогда | +1 хоп, +кросс-ядерная передача линии кэша |

### Антипаттерн: «ядро для прерываний»

Если ядро 0 только принимает IRQ и перекладывает работу на ядро 1, вы добавляете к каждому пакету передачу cache line между ядрами (десятки–сотни нс) и точку неопределённости. Для метрик это хуже, чем обработать пакет там же, где пришло прерывание.

## Влияние на планируемые алгоритмы

### Межпакетные интервалы (inter-arrival)

Самое хрупкое. Если data plane обрабатывает порцию из N пакетов разом (batching), программные метки дают интервалы, квантованные периодом опроса: гистограмма будет описывать **ваш цикл**, а не сеть. Варианты:

- аппаратные метки RX в дескрипторе (L0) — тогда batching безопасен;
- без L0 — брать `CNTPCT_EL0` при разборе каждого дескриптора **до** батчинга (метка привязана к пакету, а не к моменту обработки);
- бюджет порции мал (например, 8 пакетов), если нужны мелкие интервалы.

### EMA для RTT и джиттера

Два практических капкана:

1. **α на отсчёт vs α на время.** При `new = α·x + (1−α)·old` постоянная времени зависит от pps: при 1 pps и при 100 kpps «память» EMA отличается в 100 000 раз. Нужна либо привязка к времени (`dt`), либо фиксированные окна.
2. **Оценка σ по EMA.** Для порога «3–4 сигмы» нужен устойчивый σ; на тяжёлых хвостах EMA-дисперсия запаздывает и даёт ложные срабатывания. Обычно берут медиану/MAD или лог-шкалу.

### TTL entropy

Тут в формулировке перепутано направление: «значения TTL размазаны» — это **высокая** энтропия, а не низкая. Для легитимной подсети TTL принимает 2–3 значения (64/128/255 минус число хопов) — низкая энтропия это норма. Сильный сигнал — не энтропия сама по себе, а:

- скачок TTL при неизменной паре IP/MAC;
- несоответствие TTL заявленной ОС (fingerprint: TTL + window size + TCP options + IP ID);
- смесь TTL, несовместимая с топологией (хост за одним шлюзом).

TTL-анализ не требует точного времени — только разбора заголовка. Его можно делать на любом ядре.

## Решение (предварительное)

1. **Ядро 0 — data plane.** Run-to-completion, таймстамп L0/L1 до очереди, бюджет порции, никаких `println!`.
2. **Ядро 1 — control plane.** Executor ([[0006_data_plane_async]]): ARP-таймеры, телеметрия, конфиг, watchdog. NIC-IRQ на это ядро **не** маршрутизировать.
3. **Ядра 2–3 — припаркованы**, пока нет задачи, которую нельзя решить иначе (например, тяжёлый DPI на копии трафика — но это уже offline-анализ, не горячий путь).
4. **Метрики — per-core.** Счётчики и гистограммы пишет только владелец ядра, читает control plane. Общие счётчики на одной cache line из разных ядер = false sharing и джиттер.
5. **SPSC-очереди** между ядрами: индексы на разных cache line (`#[repr(align(64))]`), `Release`/`Acquire`, `sev`/`wfe` вместо SGI для пробуждения.

## Последствия

- + изоляция: control plane не может испортить тайминг data plane;
- + метрики не зависят от загрузки второго ядра;
- + путь к SMP постепенный: сначала 2 ядра, потом остальные;
- − нужен per-core init GIC/MMU/VBAR (сейчас `gic.rs` этого не умеет);
- − нужен PSCI и per-core стеки;
- − на QEMU TCG эффект изоляции не измерить: только функциональная проверка.

## Уточнение: одна очередь ≠ конец SMP

По вторичным данным (не подтверждено, [[ethernet_queues_ptp]]) оба интерфейса — однопоточные: у GMAC в DT `rx-queues-to-use = <1>`, у RTL8111H один ring на направление. Что из этого следует и что нет:

| Схема | Статус при одной очереди |
|---|---|
| Аппаратный RSS / несколько RX-очередей | **невозможно** |
| Flow sharding по ядрам в софте | возможно, но TX всё равно сериализуется одной очередью |
| Порточное разделение (ядро на NIC) | возможно, но форвардинг A→B идёт через межъядерную передачу |
| **Ядро 0 — DP, ядро 1 — CP** | **работает**: IRQ не идёт на ядро 1, очередей не нужно |

Поэтому пункт 1 решения не меняется: изоляция плоскостей остаётся, отменяется только идея распараллелить *приём*.

## Открытые вопросы

> [!question]
> - Сколько RX/TX-очередей у GMAC RK3566 и у RTL8111H? Предварительно — по одной у каждого. Проверить по DTB/TRM: [[ethernet_queues_ptp]].
> - Есть ли PTP-метки в дескрипторах и включаются ли они для **всех** пакетов (`TSENALL`), а не только для PTP-сообщений? От этого зависит, безопасен ли batching для inter-arrival.
> - Какой физический порт — GMAC, а какой — RTL8111H, и какой из них WAN?
> - Какой pps ожидается в реальности: 1–5 kpps (домашний роутер) или near line-rate?
> - Нужна ли реакция в реальном времени (tarpit/drop) или достаточно офлайн-анализа метрик?
