# Ethernet: очереди и аппаратные таймстампы (статус: не подтверждено)

> [!abstract] Суть
> Сведения ниже получены из вторичных источников (mainline DTS, TRM родственного SoC, результаты поиска). Для RK3566 + RTL8111H они **не подтверждены** и не должны становиться основанием архитектуры, пока не проверены по TRM/DTB/железу. Каждое утверждение помечено статусом и способом проверки.

## Утверждения и их статус

| # | Утверждение | Статус | Как проверить |
|---|---|---|---|
| 1 | GMAC RK3566 — DWMAC 4.20a, один контроллер | вероятно | mainline `rk3566.dtsi`: `compatible = "rockchip,rk3568-gmac", "snps,dwmac-4.20a"` |
| 2 | В DT Linux принудительно `rx-queues-to-use = <1>`, `tx-queues-to-use = <1>` | вероятно | тот же DTS-узел `gmac` |
| 3 | RTL8111H — одна RX и одна TX очередь | вероятно | datasheet + `r8169` (один ring на направление) |
| 4 | В GMAC есть PTP-таймстамп в RX-контекстном дескрипторе (`RDES1`/`RDES2`) | вероятно, но детали важно сверить | TRM RK3566, раздел GMAC: формат дескриптора, бит `CTXT`/`TSA` |
| 5 | Таймстамп ставится **каждому** пакету | **скорее нет** | нужен бит `TSENALL` в `MAC_Timestamp_Control`; по умолчанию DWMAC метит только PTP-сообщения |
| 6 | TX-таймстамп тоже приходит в дескрипторе | **не подтверждено** | в DWMAC TX-метка часто читается из FIFO-регистра `MAC_Timestamp_Status`, а не из дескриптора |
| 7 | RTL8111H умеет PTP через MMIO-регистры, но не через дескрипторы | **не подтверждено** | datasheet RTL8111H, регистры PTP; `r8169_ptp_*` |
| 8 | «SMP data-plane на этом железе невозможен» | **вывод слишком широкий** | см. ниже |

> [!warning] Источник
> Часть выводов опирается на TRM **RK3506** «то же IP-ядро». Это соседний SoC с другим классом ядер; совпадение IP нужно проверять по TRM RK3566, а не переносить по аналогии.

## Очереди и SMP: что именно невозможно

Невозможно **аппаратное распараллеливание приёма** (RSS/несколько RX-очередей) — если очередь одна, её владелец один. Но из этого не следуют два других вывода:

- **Изоляция плоскостей не требует очередей.** Ядро 0 — data plane, ядро 1 — control plane: NIC-IRQ идёт только на ядро 0, второе ядро вообще не касается трафика. Это работает при одной очереди и остаётся полезным ([[0007_core_partitioning]]).
- **Программный flow sharding возможен, но не нужен.** Один владелец кольца раздаёт пакеты рабочим по хэшу потока. TX всё равно сериализуется одной очередью и одним doorbell — потолок остаётся.
- **Порточное разделение** (ядро на интерфейс) технически возможно: у каждого NIC своя очередь. Цена — передача пакета между ядрами при форвардинге A→B, то есть лишний хоп в горячем пути.

## PTP: три ловушки, которых нет во вторичном разборе

### 1. Метка не бесплатна и не для всех пакетов

В DWMAC таймстампы включаются через `MAC_Timestamp_Control`:

- `TSENA` — включить;
- `TSCFUPDT` — режим fine/coarse update;
- `TSINIT`, `TSUPDT` — инициализация/подстройка PTP-часов;
- **`TSENALL`** — «timestamp all packets». Без него метку получают только пакеты, распознанные как PTP-сообщения (Sync, Delay_Req, Pdelay…).

Если `TSENALL` не поддержан конкретной конфигурацией железа, тезис «каждый пакет несёт свою метку» ложен, и inter-arrival по меткам построить нельзя.

### 2. Два разных часовых домена

PTP-таймер в MAC — **отдельный счётчик**, не `CNTPCT_EL0`. Следствия:

- дельты **внутри одного интерфейса** корректны (одно свободно бегущее 64-битное число);
- дельты **между интерфейсами** (GMAC → RTL8111H) без оценки смещения часов невалидны;
- смешивать `CNTPCT` и MAC-метку в одной метрике нельзя.

Если RTL8111H не даёт аппаратных меток, единственный корректный способ — приводить всё к одному домену: читать оба счётчика в одном ISR и поддерживать скользящую оценку смещения, либо мерить RTL-порт программно (L1).

### 3. Что именно измеряет MAC-метка

Точка отсчёта — граница MAC/MII (настраивается по TRM). Туда **не входят** задержка PHY, преамбула, провод. Для inter-arrival и для «насколько быстро отвечает узел» это хорошо: метка честно отражает момент на интерфейсе. Но это не «время на проводе» в физическом смысле.

## Как проверить (конкретный план)

1. DTS: `dtc -I dtb -O dts` по DTB платы (или mainline `rk3566.dtsi`) → узел `gmac`: `compatible`, `snps,rx-queues-to-use`, `snps,tx-queues-to-use`, число `interrupts`, наличие `snps,ptp-ref-clk`.
2. TRM RK3566, раздел GMAC: `MAC_Timestamp_Control` (есть ли `TSENALL`), формат нормального и контекстного дескриптора, поведение `MAC_Timestamp_Status`.
3. Datasheet RTL8111H: наличие и карта PTP-регистров.
4. Эксперимент на железе: включить timestamp-all, прогнать не-PTP трафик, проверить, что бит «timestamp available» поднимается и значение растёт с ожидаемой частотой.
5. Проверить, какой физический порт — GMAC, а какой — RTL8111H (схема платы/`aliases` в DTB). Для детекции сканирования нужен **WAN**-интерфейс, а не «самый удобный».

## Подводные камни

> [!warning]
> - Контекстный дескриптор занимает место в кольце: драйвер должен резервировать слот и учитывать его при подсчёте пакетов.
> - Переполнение FIFO меток → бит «timestamp dropped»; пакет приходит без метки. Логика обязана это переносить.
> - Кэш: контекстный дескриптор пишется DMA — нужна инвалидация, как и для обычного дескриптора.
> - QEMU virt (`virtio-net`) не воспроизводит ни PTP, ни DWMAC: код меток тестируется только на плате, нужен программный backend-заглушка.
> - Включение timestamp-all увеличивает объём DMA-записей; на 1.49 Mpps это заметно.
