# FP/SIMD в ядре: FPEN и trap EC=0x7

> [!abstract] Суть
> Bare-metal AArch64 стартует с `CPACR_EL1.FPEN = 0`: любая NEON/FP-инструкция ловит исключение с `EC=0x07`. Компилятор всё равно генерирует NEON — например, инициализация `[u8; 64]` превращается в `movi v0.16b` + `stp q0`, а `memcpy`/`memset` из `compiler_builtins` тоже могут его использовать. Выбор: включить FPEN и **сохранять `q8`–`q15` в контексте задачи**, либо пытаться жить без SIMD (хрупко).

## Симптом

```text
PANIC: SYNC: EC=0x7 ISS=0x1e00000 FAR=0x0 ELR=0x42001040
```

- `EC=0x07` — «SVE/Advanced SIMD/FP access trapped».
- `FAR=0x0` — адрес невалиден, потому что это не обращение к памяти.
- `ELR` указывает на инструкцию **внутри обычной функции**, где нет явной математики. В нашем случае `0x42001040` = `task_a + 8`, где инициализируется маркер `[0xA5u8; 64]`.

## Почему компилятор использует NEON

- `[0xA5; 64]` — это 64 байта; LLVM сворачивает их в `movi v0.16b, #0xa5` + несколько `stp q0`.
- `core::hint::black_box` копирует значение — при 64 байтах тоже появляется `ldp/stp q`.
- `memcpy`/`memset` из `compiler_builtins` и часть `core` собраны для этого таргета с включённым NEON.
- `-C target-feature=-neon` действует на **ваш** крейт; предсобранный `core` остаётся с NEON. Поэтому «просто выключить» — не гарантия.

> [!warning] Ловушка только на первом обращении
> Паники не будет в коде без NEON-инструкций, и из-за этого баг «переезжает»: стоит добавить массив/копирование/хеш — и падает там, где раньше работало.

## Вариант A: включить FP/SIMD (рекомендуется)

```asm
mrs x0, cpacr_el1
orr x0, x0, #(3 << 20)   // FPEN = 0b11: FP/SIMD разрешён на EL0/EL1
msr cpacr_el1, x0
isb
```

Место — `_start` **до** `bl main`: после возврата в Rust уже нельзя гарантировать, что первая инструкция не окажется SIMD. `CPACR_EL1` — per-core, для SMP настраивается на каждом ядре.

> [!warning] Где именно вставлять (и чем это опасно)
> Не между `ldr x0, =__bss_start` и циклом обнуления: `mrs x0, cpacr_el1` затрёт **курсор** `.bss`, и `stp xzr, xzr, [x0], #16` начнёт писать по адресу вида `0x300000`. В QEMU там нет RAM → abort до установки `VBAR` → **ни одной строки в UART**; выглядит как «зависло без вывода».
>
> Безопасные варианты: (а) скретч-регистр `x2`/`x3` вместо `x0`; (б) вставить блок **до** загрузки `x0`/`x1`; (в) сразу перед `bl main`. Класс ошибки общий: между «загрузил указатели» и «использую их в цикле» нельзя брать те же регистры под что-то ещё.

### Тогда обязательно сохранять SIMD

AAPCS64: `v8`–`v15` (полные `q8`–`q15`) — **callee-saved**. Значит, для корректности через вызовы (`yield_now` → `sched_switch`) достаточно сохранять их. `v0`–`v7`, `v16`–`v31` — caller-saved, их компилятор сам сбросит на стек перед вызовом.

Раскладка при добавлении в `TaskContext`:

```text
0    x19…x30 (12 × 8)
96   sp                      (8)
104  padding до 16
112  q8,  q9                 (2 × 16)
144  q10, q11
176  q12, q13
208  q14, q15
240  = size
```

В asm:

```asm
stp q8,  q9,  [x0, #112]
stp q10, q11, [x0, #144]
stp q12, q13, [x0, #176]
stp q14, q15, [x0, #208]
```

и симметричные `ldp` при загрузке. Для новой задачи `q8`–`q15` = 0 — валидное начальное состояние callee-saved.

> [!warning] Включить FPEN и не сохранять SIMD — хуже, чем не включать
> Получите не панику, а тихую порчу значений между задачами. Ошибка проявится через минуты работы и в другом месте.

`FPCR`/`FPSR` (режим округления, флаги) — общее состояние; для ядра без floating-point их можно не сохранять. Как только появятся `f32`/`f64`, добавьте и их (или запретите FP в коде и оставьте только SIMD-копирование).

## Конкретная правка `TaskContext`

`TaskContext` — не «удобная структура», а **снимок регистров в памяти**: `sched_switch` пишет и читает поля по фиксированным смещениям. Поэтому «добавить `q8`–`q15`» = добавить поля, которые лягут на нужные смещения.

### Было

```rust
#[repr(C)]
#[derive(Clone, Copy, Default)]
pub struct TaskContext {
    pub x19: u64,
    // … x20 … x29 …
    pub x30: u64,
    pub sp: u64,
}

const _: () = assert!(core::mem::offset_of!(TaskContext, sp) == 96);
const _: () = assert!(core::mem::size_of::<TaskContext>() == 104);
```

### Стало

```rust
#[repr(C)]
#[derive(Clone, Copy, Default)]
pub struct TaskContext {
    pub x19: u64,
    pub x20: u64,
    pub x21: u64,
    pub x22: u64,
    pub x23: u64,
    pub x24: u64,
    pub x25: u64,
    pub x26: u64,
    pub x27: u64,
    pub x28: u64,
    pub x29: u64,
    pub x30: u64,
    pub sp: u64,

    // --- новое: callee-saved SIMD ---
    pub q8: u128,
    pub q9: u128,
    pub q10: u128,
    pub q11: u128,
    pub q12: u128,
    pub q13: u128,
    pub q14: u128,
    pub q15: u128,
}

const _: () = assert!(core::mem::offset_of!(TaskContext, sp) == 96);
const _: () = assert!(core::mem::offset_of!(TaskContext, q8) == 112);
const _: () = assert!(core::mem::offset_of!(TaskContext, q15) == 224);
const _: () = assert!(core::mem::size_of::<TaskContext>() == 240);
```

Смещения:

| Поле | Смещение | Размер |
|---|---|---|
| `x19`…`x30` | 0…88 | 96 |
| `sp` | 96 | 8 |
| *паддинг* | 104 | 8 |
| `q8`/`q9` | 112 | 32 |
| `q10`/`q11` | 144 | 32 |
| `q12`/`q13` | 176 | 32 |
| `q14`/`q15` | 208 | 32 |
| **size** | | **240** |

> [!warning] Почему `u128`, а не `[u64; 2]`
> `u128` на AArch64 имеет `align = 16` → `q8` встаёт на 112, и все `stp q…, [x0, #imm]` получают `imm`, кратный 16 (обязательное требование для 128-битного `stp`). У `[u64; 2]` выравнивание 8: `q8` оказался бы на 104, а `stp q8, q9, [x0, #104]` — невалидная инструкция.
> Восемь байт паддинга (104…112) вставляет компилятор по правилам `#[repr(C)]`; const-assert'ы как раз затем, чтобы это не разъехалось молча.

### asm

В `sched_switch` — сохранить SIMD рядом с GPR, до сохранения `sp`:

```asm
sched_switch:
    stp x19, x20, [x0, #0]
    stp x21, x22, [x0, #16]
    stp x23, x24, [x0, #32]
    stp x25, x26, [x0, #48]
    stp x27, x28, [x0, #64]
    stp x29, x30, [x0, #80]
    stp q8,  q9,  [x0, #112]
    stp q10, q11, [x0, #144]
    stp q12, q13, [x0, #176]
    stp q14, q15, [x0, #208]
    mov x9, sp
    str x9, [x0, #96]

    ldr x9, [x1, #96]
    mov sp, x9
    ldp x19, x20, [x1, #0]
    ldp x21, x22, [x1, #16]
    ldp x23, x24, [x1, #32]
    ldp x25, x26, [x1, #48]
    ldp x27, x28, [x1, #64]
    ldp x29, x30, [x1, #80]
    ldp q8,  q9,  [x1, #112]
    ldp q10, q11, [x1, #144]
    ldp q12, q13, [x1, #176]
    ldp q14, q15, [x1, #208]
    ret
```

В `sched_start` то же самое, но только `ldp` (сохранять нечего):

```asm
sched_start:
    ldr x9, [x0, #96]
    mov sp, x9
    ldp x19, x20, [x0, #0]
    …
    ldp x29, x30, [x0, #80]
    ldp q8,  q9,  [x0, #112]
    ldp q10, q11, [x0, #144]
    ldp q12, q13, [x0, #176]
    ldp q14, q15, [x0, #208]
    ret
```

> [!warning] Порядок обязателен
> `stp q…` сама требует `FPEN`: если включить сохранение SIMD, но не включить `CPACR_EL1.FPEN`, trap `EC=0x7` переедет в `sched_switch`. FPEN включается в `_start` до `bl main`.

### `spawn`

Если используется `TaskContext { sp, x30, ..Default::default() }`, менять `spawn` **не нужно**: `Default` даёт нули и для `q8`–`q15`, а нули — валидное начальное состояние callee-saved регистров. Если поля присваиваются по одному — придётся перечислить все восемь `q`.

> [!warning] `const`-инициализаторы
> В `Task::UNUSED` (и любом другом `const`) `..Default::default()` не сработает: `Default::default()` — не `const fn`. Там поля перечисляются явно, поэтому после добавления `q8`–`q15` в литерал нужно добавить восемь `q…: 0`. Иначе — `E0063: missing fields … in initializer of TaskContext`.
>
> Чище — завести один `TaskContext::ZERO` const и использовать его в `Task::UNUSED`; тогда полный список полей живёт в одном месте — рядом с `offset_of!`-assert'ами.

### `sched_start` тоже обязан восстанавливать SIMD

В `sched_switch` есть и `stp`, и `ldp`. Но `sched_start` используется не только для первого запуска: через него `exit()` прыгает в следующую задачу. Значит, из него тоже нужны четыре `ldp q8..q15` — иначе возобновлённая задача получит чужие callee-saved SIMD-регистры (тихая порча, а не паника).

## Вариант B: жить без SIMD

- Убрать «вектороопасные» конструкции: большие массивы, `memcpy`, `black_box` на больших значениях.
- Проверять `.text` на `movi v…`, `stp q…`, `ldp q…`, `dup v…`.
- Помнить, что `core`/`compiler_builtins` могут подсунуть NEON независимо от вашего кода.

Годится для минимального ядра, но как только появятся хеширование, крипто, DPI — придётся вернуться к варианту A.

## Как проверить

| Что | Как |
|---|---|
| Ловится ли trap | лог QEMU: `EC=0x7`, `FAR=0` |
| Есть ли SIMD в образе | `llvm-objdump -d` и поиск `movi v`, `stp q`, `ldp q` |
| Включён ли FPEN | прочитать `CPACR_EL1` через GDB: `p/x $cpacr_el1` |
| Регресс | после включения FPEN тот же сценарий проходит; `schedtest` доходит до вердикта |

## Подводные камни

> [!warning]
> - `CPACR_EL1` — per-core; на вторичных ядрах нужно повторить.
> - После записи `CPACR_EL1` обязателен `isb`.
> - Добавление `u128` в `TaskContext` меняет выравнивание структуры на 16; смещения `q8…` начинаются с 112, а не 104.
> - `stp q` сам требует включённого FPEN — порядок «включить, потом использовать» обязателен.
> - FPEN=0b11 разрешает FP/SIMD и на EL0; для ядра без пользовательского режима это не проблема.
> - QEMU `virt` эмулирует FP/SIMD, поэтому trap воспроизводится и без платы.

## Источники
- ARM ARM (DDI 0487): `CPACR_EL1.FPEN`, `ESR_EL1.EC = 0x07`.
- AAPCS64: callee-saved `v8`–`v15`.
